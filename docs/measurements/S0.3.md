## Executive summary (Windows development machine, non-certifying)

1. **Worker startup & first sample (`SB3`, target < 150 ms):** on the refreshed post-review
   campaign (rebuilt `libngspice-0.dll`, run under active background build contention on the
   development laptop), cold `omnia-ngspice-worker` spawn + `libngspice-0.dll` load + Wien
   oscillator `TRAN` time-to-first-sample had a median run p99 of **116.48 ms** (p50
   **29.88 ms**, quiet rep-0 p99 **17.81 ms**; cold OP median run p99 **64.06 ms**, p50
   **32.63 ms**; warm worker reuse median run p99 **16.67 ms**, p50 **3.53 ms**, vs in-process
   median run p99 **1.69 ms**, p50 **1.24 ms**) — still below the 150 ms `SB3` budget even
   under heavy background contention. (In the quieter initial pre-review campaign on the same
   machine, cold Wien first-sample was **15.17 ms** median run p99.)
2. **Binary `f64` streaming throughput (target >= 100 kS/s):** streaming 100,012 accepted time
   points × 2 probe channels (24 bytes/point, 256-point batches) over binary stdio frames
   reached a true even-N median of **246,004 points/s (492,008 channel-samples/s)** vs
   **268,204 points/s (536,408 channel-samples/s)** in-process (**~5× above** the 100 kS/s
   target; in the quieter pre-review run, **748,450 pts/s** vs **780,385 pts/s**). The
   end-to-end streaming difference (~8.3% under contention; ~4.3% when quiet) reflects total
   execution differences — worker background-thread scheduling (`bg_run` vs synchronous `run`),
   mutex-guarded stdio sink batching, framing, and OS pipe transfer — not pure IPC serialization
   overhead alone.
3. **Cancellation & orphan isolation (`SB4`, target < 100 ms; `SINV5`):**
   - **Critical finding:** upstream `ngspice-47` `_thread_stop()` (`src/sharedspice.c:562`)
     unconditionally executes `Sleep(100)` per poll tick on Windows (`usleep(10000)` on Unix).
     Consequently, `inproc-cancel-bghalt` takes **120.33 ms** median run p99 (p50 **112.76 ms**,
     range 115.65–139.20 ms) — **exceeding `SB4` (100 ms) on Windows**.
   - With the `SK11` 50 ms deadline enforced across the entire cooperative cancel + worker exit
     + `try_wait`/reap path, all **50/50** Windows `worker-cancel-coop-kill` runs exceeded the
     50 ms grace because of `Sleep(100)` and honestly fell back to hard-kill (`cancel_coop_stops = 0`,
     `cancel_hard_kill_fallbacks = 50`, p50 **75.71 ms**, median run p99 **129.17 ms** with one
     2,010 ms OS-contention outlier).
   - Direct `worker-cancel-hard-kill` (killing and reaping the isolated worker subprocess)
     takes **30.51 ms** median run p99 (p50 **15.96 ms**, max **49.67 ms** under contention;
     **2.25 ms** p99 when quiet) with **0 orphan processes** verified across all 100 worker
     cancellations. This strongly supports `SD5` worker isolation (and shows `S1.6` should kill
     the worker directly on Stop while reserving `bg_halt` for Pause/Resume).
4. **Licence audit finding (`SD12`, `SINV11` — requires owner decision before `S1.6` / `HS2`):**
   - **Dynamic dependencies:** zero third-party GPL/LGPL libraries are dynamically linked
     (`objdump -p` and `ldd` show only Windows system DLLs, UCRT, and MinGW/GCC runtimes).
     Every optional GPL/LGPL/MPL module (`KLU`, `fftw3`, `readline`, `OpenMP`, `OSDI`,
     `tclspice`, and external `xspice/icm/table.cm`) is disabled or excluded from the build.
   - **Upstream static-source finding:** upstream `ngspice-47` **unconditionally statically
     compiles `src/frontend/numparam/libnumparam.la` (LGPLv2 or newer)** into `libngspice`
     (`COPYING`, `src/Makefile.am:554`) with no `./configure` switch to disable it. See the
     Licence audit section below for the exact audit and owner decision options.

### Upstream `ngspice-47` build and runtime quirks discovered for `S1.6` / `S4.2`

1. **`--disable-xspice` fails to compile in upstream `ngspice-47`:** `src/spicelib/analysis/cktsopt.c:254`
   references `OPT_ENH_RSHUNT` inside an `#else` branch of `#ifdef XSPICE`, while `optdefs.h:152`
   declares `OPT_ENH_RSHUNT` only under `#ifdef XSPICE`. Keeping `--enable-xspice` builds cleanly
   without patching upstream; every XSPICE library statically linked into `libngspice`
   (`mif`/`cm`/`enh`/`evt`/`idn`) is Public Domain (`COPYING`), and skipping `src/xspice/icm`
   avoids both the GPLv2+ `icm/table` codemodel and a GCC 15 `-Wimplicit-function-declaration`
   compile error in `src/xspice/icm/xtradev/seegenerator/cfunc.c`.
2. **`ngSpice_nospinit()` / `ngSpice_nospiceinit()` crash before `ngSpice_Init()` on Windows MinGW:**
   In `src/sharedspice.c:806-820`, both functions call `cp_vset()` → `tmalloc()` →
   `EnterCriticalSection(&allocMutex)` before `ngSpice_Init()` initializes `allocMutex` at line 904
   (on Windows builds using Win32 threads), causing an immediate `0xC0000005` access violation.
   Because Omnia ships no `spinit` or `.cm` files alongside `libngspice`, omitting pre-init
   `ngSpice_nospinit()` works cleanly on both platforms.
3. **`bg_halt` (`_thread_stop`) sleeps 100 ms per poll on Windows:** `src/sharedspice.c:562` uses
   `Sleep(100)` on Windows vs `usleep(10000)` (10 ms) on Unix. On Windows, calling `bg_halt`
   cannot finish in under 100 ms even when the solver halts in `< 1 ms`.
4. **Static MinGW runtime linking for `S4.2` Windows release bundles:** GNU libtool strips bare
   `-static-libgcc -static-libstdc++` from `LDFLAGS`, so the spike DLL dynamically imports
   `libstdc++-6.dll`, `libgcc_s_seh-1.dll`, and `libwinpthread-1.dll` from UCRT64. For a
   self-contained Windows distribution in `S4.2`, pass
   `-Wc,-static-libgcc -Wc,-static-libstdc++ -Wl,-Bstatic -lwinpthread -Wl,-Bdynamic` (or build
   with a native Windows C/C++ toolchain) and re-audit with `objdump -p`.

> [!IMPORTANT]
> **Owner decision required for `SD12` / `SINV11` before `S1.6` and `HS2`:**
> Upstream `ngspice-47` has no configure flag to omit `src/frontend/numparam` (LGPLv2+), because
> `src/frontend/inp.c`, `inpcom.c`, and `measure.c` call `nupa_*` unconditionally. Consequently,
> any unmodified upstream `libngspice` shared library contains statically compiled LGPLv2+ code
> from `numparam` alongside its BSD-3-Clause core. Because `S0.3` must not weaken `SD12` or
> `SINV11`, this is flagged as a `needs-human` decision with three clear paths for the owner:
> 1. **Amend `SD12`/`SINV11` for dynamically loaded `libngspice`:** ship unmodified `libngspice`
>    strictly as a replaceable shared library loaded via `libloading` inside the isolated
>    `omnia-ngspice-worker` subprocess (satisfying LGPLv2.1 §6 dynamic-linking obligations while
>    keeping zero GPL code and zero LGPL in any Rust crate or Omnia executable), with full source
>    tarball URL/build recipe in `THIRD_PARTY.md`.
> 2. **Patch out `numparam` in Omnia's `ngspice` build recipe:** stub `nupa_*` to no-ops (note:
>    Omnia's own netlist emitter writes plain numbers per `SINV6`, though third-party `.subckt`
>    decks using `.param` / `{expr}` would lose `ngspice` parameter evaluation unless Omnia's
>    lowering evaluates them first).
> 3. **Do not bundle `ngspice`:** make pure-Rust BSD-3-Clause `RIS-C` the sole bundled engine
>    and treat `libngspice` as an optional user-installed / CI-fetched oracle.
