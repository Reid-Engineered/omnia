# A1.1: `Doc::fork` time and size on `10k`

**Non-reference record.** It was measured on a Windows development laptop, not the Orion
reference machine, so it certifies nothing (AGENTS.md hard rule 3). No budget gates `fork` on its
own. AB2 (A1.10) gates `preview` with the fork included, on the reference machine.

## What is measured

- **Bench:** the Criterion bench [crates/omnia-bench/benches/fork.rs](../../crates/omnia-bench/benches/fork.rs).
  It forks T2.4's `10k` stress sheet (`generate(StressSheet::Parts10k, 42)`: 10,000 parts,
  20,000 wires, revision 30,000).
- **Timed span:** `Doc::fork()` only. Dropping the fork is outside the span.
- **Size:** the incremental live heap bytes of one live fork. This is the process-wide increase
  in the bytes requested from the counting allocator while the fork exists. The number of
  allocations the fork made is reported separately. It is exact and the same on every run,
  because the generator and the clone are deterministic. It is not the fork's full footprint:
  text the fork shares with the original (`Arc<str>`) is not copied, and allocator overhead is
  outside the counter. The bench prints it as `fork_heap_bytes`.
- **Schedule:** 10 repetitions of the one frozen case, `fork_10k`. With a single case, rotation
  is trivial. Each invocation records 100 `Instant` observations, reported as nearest-rank p50
  and p99, with no warm-up discarded. Criterion follows (`sample_size = 20`, warm-up 1 s,
  measurement 4 s, `--noplot`). The schedule, case and binary were fixed before the first timed
  run. There were no retries and nothing was discarded.
- **Script:** [A1.1/run.ps1](A1.1/run.ps1), with the summary from [A1.1/summarize.py](A1.1/summarize.py).
- **Raw data:** [A1.1/windows/raw.tar.gz](A1.1/windows/raw.tar.gz) holds the per-pass CSVs and
  stdout, the order file, condition snapshots before and after each pass, and `machine.json`
  (binary SHA-256, git head, source hashes). [A1.1/windows/summary.txt](A1.1/windows/summary.txt)
  holds the summary.

## Results

| | Value |
| --- | ---: |
| Median of run p99s | **9.419 ms** (range 8.222 to 13.055) |
| Median of run p50s | 7.473 ms (range 7.026 to 9.947) |
| Criterion point estimates, 10 runs | 7.249 to 8.380 ms |
| Incremental live heap bytes, one live fork | **17,296,160 bytes** (16.50 MiB) |

The allocation count is dominated by the per-cell vectors of the spatial index and the
connectivity tables. The fork copies the index and the connectivity rather than rebuilding them.
The fork's memory is recorded against B9 at A1.10 (AB2), as mcp-plan.md section 15 says.

## Review notes

The independent review of PR #82 found that the campaign script writes `order.txt` only after
all passes succeed, and that `summarize.py` does not check for 100 samples per pass. Neither
script was changed after this campaign, so that the committed scripts match the hashes in
`machine.json`. This campaign completed: the archive holds all ten passes with 100 samples
each, and the review reproduced the 9.419 ms median p99 from it. A later campaign built on these
scripts should write the planned order before timing, mark an aborted run `INCOMPLETE` and keep
its partial evidence, and validate the pass and sample counts before summarising.
