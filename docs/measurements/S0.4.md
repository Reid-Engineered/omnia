# S0.4 / SS2 Live oscilloscope ring-buffer overhead

**Roadmap status is `needs-human`.** The Orion campaign is pending. SK8 remains at the 30 Hz default.

## Workload

`omnia-bench spike sim-scope` opens the standard 1k sheet (seed 42, 1,000 parts and
2,000 wires) with a 576 × 468 logical-pixel scope above it. The benchmark requests a
window frame each refresh in both cases so B3 can use the same 60 Hz present-interval
rule. At 30 Hz the scope drains and repaints on alternate frames. Both cached views
replay on the intervening frames. At 60 Hz the scope updates every frame. The sheet
remains static during the run. The counter increments when the actual `SheetView`
paint runs (D7, G6, SINV9).

SS2 counts window frames with `frame.is_multiple_of(60 / hz)`. At Orion's verified
59.9–60.1 Hz refresh rate, every other frame is approximately 33.3 ms, matching
the interval of the SK8 default timer.

The background producer emits a pair of timestamped synthetic signals at 100,000
sample pairs per second, equivalent to 100 kS/s per channel. It derives the sample
index from elapsed wall time and publishes in batches. The shared SPSC ring stores
65,536 `[Sample; 2]` pairs, preserving SK6's 1 MiB per channel and 2 MiB total. It
drops new pairs when full and counts them. D8 specifies a ring per channel, and
SK6 states the capacity per channel. In S3.3, use per-channel rings or update the
plans if the shared ring is adopted. The scope drains published pairs into a
preallocated rolling 2,048-pair trace and paints a 512-column min/max envelope
for each channel.

Frame work and CPU-side present intervals come from the pinned GPUI profiler after
warm-up. Raw misses count present intervals over 1.5 refresh periods. The shared
[B3 attribution](T1.6/attribute.py) identifies the documented compositor-side
exclusion using the recorded frame and foreground traces. Allocations use the bench
counter (B10, Q5). Its Omnia scopes cover ring publication, scope drain and paint,
sheet paint, and per-frame recording. GPUI scene, layout and rendering allocations
are included in totals. S3.3 should decide whether element-tree construction in
`ScopeView::render` and `RunView::render` also belongs in `ours`. Memory samples
cover the sheet and prototype scope in the benchmark process. The full SB6 workload
with a solver and Results dock is measured in S4.4.

## Orion

From a clean checkout containing S0.4, at the Orion desk in the local Wayland
session, close other apps, connect AC, set the CPU governors to `performance`, and
keep the native panel awake and the benchmark in the foreground. Run the campaign
with the following command.

```sh
python3 -B docs/measurements/S0.4/run.py orion ~/omnia-s04-orion
```

The runner builds the release binary once. At 100% and 125% scaling it runs 600
warm-up and 600 measured frames per case, interleaving ten repetitions of each
cadence and reversing their order on even repetitions. It records the frozen order,
binary fingerprints, before and after conditions, compressed raw reports, and B3
attribution. It restores the original scale when the campaign exits. Read the
median and range of run p99s in `summary.json`, plus the counted misses across all
runs. Assess B3 (<16.7 ms p99 and zero counted misses), B5 (≤33.3 ms maximum), and
SINV9 (zero sheet paints and zero warm Omnia allocations) against SB5. Only the
Orion evidence can justify moving SK8 to 60 Hz.

## Windows diagnostic

The laptop is an ASUS TUF Gaming F16 (FX608JMR) with an Intel Core i7-14650HX
(16 cores, 24 logical CPUs), 31.61 GiB of usable RAM, and Windows 11 Home 25H2
(build 26200.9974, x64). GPUI selected Intel UHD Graphics (driver 32.0.101.7088).
The other adapter is a GeForce RTX 5060 Laptop GPU (driver 32.0.15.9191).
The built-in display is 1920 × 1200 at 60 Hz and 125% scaling. The window content
was 1536 × 864 logical pixels (1920 × 1080 device pixels). The machine was on
battery with Windows processor power management on its Silent power plan.

The [initial campaign](S0.4/windows-incomplete/status.txt) stopped in repetition 4
at 60 Hz. GPUI drew 120 measured frames and recorded 79 present intervals. The
process snapshots show other GUI tests running on the same desktop. That
interference justified rerunning the full schedule after the other tests finished.
The first six reports and the failed invocation are retained.

The [complete campaign](S0.4/windows-diag/summary.json) used the same release
binary after the other test runs finished. Each cadence ran ten times in rotating
order, with 60 warm-up and 120 measured frames per run.

- **30 Hz.** Median run p99 was 0.840 ms (range 0.570–0.981 ms), and the
  longest frame was 1.475 ms. Scope paint cadence was 29.954–30.085 Hz.
  Peak sampled private memory was 99.102 MiB, and peak sampled working set was
  101.609 MiB. All 600 scope updates drained samples.
- **60 Hz.** Median run p99 was 0.814 ms (range 0.740–1.003 ms), and the
  longest frame was 1.279 ms. Scope paint cadence was 60.049–60.179 Hz.
  Peak sampled private memory was 99.106 MiB, and peak sampled working set was
  101.637 MiB. Of 1,200 scope updates, 55 found no newly published pairs and
  repainted the existing trace. The roughly 15.6 ms default Windows timer
  resolution can delay the producer's requested 2 ms wait, so a 60 Hz scope
  update can arrive before the next batch.
- Across both cadences, there were zero dropped pairs, zero sheet paints, zero
  warm Omnia allocations, and zero missed refreshes. The measured attempted
  producer rate ranged from 99,450 to 100,346 pairs/s. Median run means for
  total allocations were 20.53/frame at 30 Hz and 21.03/frame at 60 Hz.

The complete campaign directory also contains the binary fingerprints,
conditions, run order and compressed raw JSON for all 20 runs.

## Checks

The release build, all five standard checks, and the three focused SS2 tests
passed locally on Windows. The three tests cover SK6 wraparound and drops,
concurrent FIFO delivery and drop accounting, and zero allocations in the warm
ring and trace update path (SINV9).
