# W1.5 measurements: one `route` call

Not the reference machine. These figures gate nothing; W1.5 has no budget.

**Diagnostic record, not a section 2.1 campaign.** The done-when asks that a criterion bench
records the time for one `route` on `10k` and on `dense`. This is one invocation, not ten
interleaved rotating repetitions, and no raw samples, order file or condition snapshots were
kept. Treat the numbers as indicative only.

## Cases

For every pair of consecutive parts (by id) the bench routes from the first part's first pin
moved one grid step down (where a follow would start) to the next part's first pin, with
`first_leg` alternating. The old wiring is left in the document, so the moved end often sits
on the part's own wires: on `dense` (12 rays per first pin) every case is refused, which is
the worst case for `route`: every candidate (up to 2 + 128) is scored and validated. On `10k`
most cases succeed. Scratch and output are warm (no allocation; see
`crates/omnia-doc/tests/route_alloc.rs`). The observation line times every case once; the
criterion line cycles through them.

## Reading

`route` scores every candidate before validating any (the score needs one local index query
per segment), then validates in score order and stops at the first valid one. A refusal
validates all of them, so refusals and long spans make the tail: the p99 is about ten times the
median on both sheets. WB1 (0.5 ms p99 for a whole one-part follow with up to 9 runs) is
W2.5's gate on the reference machine. Nine routes at the `10k` mean fit it easily; nine at the
refusal tail would not, so W2.1/W2.4 should measure `bench follow` with the old run removed
before routing, as the planner will do. If the tail matters there, the per-candidate index
queries are the place to optimise (for example one query over the box all candidates share,
filtered per segment); the first score term needs the geometry, so it cannot be skipped.
