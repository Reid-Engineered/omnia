## Acceptance semantics

Plan D8 says incremental connectivity runs inline, targeting **under 1 ms per command
at 10,000 parts**. T2.8 additionally asks whether one add/remove stays under 1 ms on
the real `10k` and worst cases. Section 2.1 explicitly gates on **the median of ten
run p99s**, reporting the range, with cases interleaved and their order rotating.
Thus neither a Criterion mean nor an isolated maximum substitutes for the gate.
The existing harness's `over_1ms` counter counts observations **>=** 1 ms, consistent
with strict "under"; those counts are retained as diagnostics, not a new all-samples
gate. INV10 is a correctness requirement, not a timing statistic. B9 is the separate
300 MB rendering memory budget; this CPU run makes no B9 claim.

## Isolation of the problem and proposed follow-up

The failing workload has no labels or parts: it isolates geometric splitting, not
label-net reflood, Doc indexing, rendering, loading, or sheet generation. Removing
the middle wire leaves both endpoints alive, so `Connectivity::remove_wire` takes
its general path and calls `flood_from` twice to rebuild the two halves. Source
inspection shows full point/wire traversal, hash-map lookups, fresh result vectors
and component membership writes. The leaf case avoids that path and is cheap.
This is evidence for investigating the split path, not a sampled CPU profile proving
which individual instruction dominates (`perf` is not installed).

Proposed next step: profile that isolated path, measure vector allocation versus
point lookup/membership costs, then evaluate scratch-buffer reuse and more direct
point traversal while preserving the independent rebuild oracle and INV10 properties.
Any algorithm change needs review and a fresh fixed ten-pass run; no broad rewrite
or threshold change is included here. A protocol-compliant acceptance run remains
necessary after a fix. Existing Windows results remain diagnostic, not a pass.
