## Review fixes (2026-11-17)

Owner answers recorded on 2026-11-17: normal form wins over WINV2 at points the moved
items vacate (WD3, WINV2 updated), and both existing-test changes above are approved.

- Selected-wire capture refusals now return `CommandError::Capture { wire, blocker }`
  instead of `FollowError::NoRoute`; the rule is in WD3 and applies under every policy.
- `Move`/`Reorient` merge collinear wires left meeting at vacated pin, end and label
  points, in detach mode as well as follow mode. The generated test asserts normal form
  in both modes.
- The mixed-edit route property no longer just tolerates refusals: a brute-force
  oracle must agree with the command in both directions (refused exactly when a capture
  exists).
- The W2.2 property test adds random foreign pins and wires around the moved part,
  asserts WINV1 directly (pairs connected before stay connected, unless the selected part
  had a direct pin contact, WQ6), and requires the command to refuse exactly when the
  planner refuses. (Coverage at this point: one moved part, no generated direct contacts,
  an all-or-nothing WQ6 exemption; widened in the second round below.) Diagnostic soak runs (release, Windows, not part of CI): 4000 cases of
  the W2.2 property and 2000 of the route property passed.
- Identity transforms: `plan_follow` can refuse a zero move (re-routing a run in place
  through foreign geometry) while the command is inert. The test treats identity
  separately. Logged for W2.1's owner: a W2.3 preview at drag start would show a refusal.
- Large selections (diagnostic, debug build, Windows, not a budget measurement): moving
  N disjoint selected wires took 59 / 152 / 451 ms for N = 2000 / 4000 / 8000, of which
  `plan_follow` was 19 / 74 / 286 ms. The planner (W2.1, `follow.rs`) is the quadratic
  part; the command path scales roughly linearly. Logged for W2.1's owner.

## Second review round (2026-11-17)

A second independent review (different model) of the fixes above found five items. All
are addressed:

- A moved label landing on a wire body now splits it (WD9). Selected labels' and
  ride-along labels' new points join the TC-move-14 landing pass.
- `CommandError::OffLattice(at)`: a move that takes an on-lattice wire end off the
  lattice, lands an off-lattice pin or label on a wire body, or makes a lattice wire
  cover an off-lattice label is refused before any edit (WK1, WINV3); the lowest point
  is reported. Ends already off the lattice are not judged, because `AddWires`
  still accepts them (pre-existing; logged). Two fixtures changed to stay legal: the
  route mixed-edit property (raw-nm sheets) now expects `OffLattice` exactly when a
  brute-force check finds an on-lattice end leaving the lattice or a lattice wire
  covering an off-lattice label (the property gains assertions), and the index_alloc
  fixture moves and pivots by one lattice step (its query area follows the move). The
  assertions in both are unchanged.
- The capture blocker is ranked from the moved wire's low corner, so stored end order
  no longer decides it (determinism). Regression test reverses a/b.
- The W2.2 property now moves one or two parts, generates direct pin contacts (foreign
  pins placed on a selected pin). Under follow, only pin pairs that include a foreign pin
  left behind at such a contact are exempt from the exact-partition and WINV1 checks;
  every other pair, including shorts to unrelated nets, is checked. Its expected partition still takes the replaced
  wires from the planner's `remove` list: it checks how the command applies a plan, not
  which runs the planner chose.
- Found by the widened generator, open for the owner: when a selected pin, a foreign pin
  and a wire end share one point, the run follows the moved pin (WD2 boundary point) and
  the foreign pin loses its wired connection. WINV1 excepts direct contacts but does not
  say which side keeps the wire. Pairs with such a pin are exempt until decided.
- WD3 wording corrected: capture is checked after planning, so `NoRoute` takes
  precedence.

Checks: see the pull request.

Re-check of the second round (same reviewer model): three follow-ups, all fixed. A lattice
wire moved over a stationary off-lattice label is refused (normalisation would split it
there); `OffLattice` names the lowest violating point, so end and item order never decide

Off-lattice legacy wire ends landing on legacy off-lattice bodies stay accepted, matching

Final re-check (same reviewer model): two follow-ups, both fixed. A legacy off-lattice end

## WB3 optimisation, Windows diagnostic (2026-11-23)

**Status: `needs-human` — awaiting an Orion re-run.** Nothing below certifies WB3 (hard
rule 3); the numbers come from a Windows development machine and are labelled
non-reference. The bench workload, its threshold and every test are unchanged (hard rule 2).

**Root cause.** `plan_follow` built its final-geometry view by copying the whole sheet
into a fresh `Doc` on every call: every part, wire, pin and point re-inserted into a new
spatial index (its full K12 grid), point map and connectivity, then dropped. On `Parts10k`
that was roughly 20 ms of the planner's time before any routing, plus the drop. Routing
then scored every WD4 candidate (34 per run here) with index queries before validating
any, and validation queried each segment twice more.

**Changes** (`crates/omnia-doc/src/`):

- `follow.rs`: the view is layered over the caller's document instead of copied. It holds
  only the moved selection, the endpoint reservations and the planned wires (in a small
  cell map), hides replaced runs and selected items by id, and gives the ids a full copy
  would (reservations after the part slots, planned wires after the wire slots). It reads
  the document's index through a new stamp-free query, so planning leaves the document
  exactly as it was, index stamps included (W2.1's purity check).
- `route.rs`: `route` scores candidates lazily, best first, against an exact lower bound
  (bends, length and number, plus the body term once the first assessment shows whether an
  end lies strictly inside a part body), and judges validity from the same per-segment
  query in one pass over its items. Candidates are checked in exactly the order of their
  full scores, so the answer equals scoring and sorting all of them (WD4, WINV6). The
  validator's rules are shared per-item helpers, so `check_new_wires` and the router
  cannot drift apart. In `plan_add_wires`, labels at a point come from the connectivity's
  point map (labels are indexed at their anchor) and per-line feature coordinates from
  sorted vectors instead of a map of vectors.
- `points.rs`: the point map uses `FxHashMap` like the rest of the document (its
  iteration order was already unspecified; it is now deterministic).
- `index.rs`: `query_filtered_unstamped`, a stamp-free filtered query.
- Public signatures are unchanged; `wiring-plan.md` wording for `route` and the W2.1 view
  note is updated.

**Equivalence evidence.** A temporary harness (not committed) kept the pre-change planner
and router side by side with the new ones: 50,000 random sheets with random selections,
moves, reorientations and policies (about 16,700 non-empty plans, 7,800 of them rerouting,
and 1,100 refusals) gave identical `FollowPlan`s and identical errors, and the two agree on
the seed-42 `Parts10k` WB3 workload. It ran after each router change; the last two view
changes (stamp-free reads, bounds stored with the view's cells) came after it and are
covered by the permanent view-vs-copy property below. Permanent tests added: `follow::view_tests::w22_view_reads_as_the_full_copy`
(the layered view answers every query, pin, wire, body and wire-end lookup exactly as a
full copy, ids included, and planning leaves the document's `Debug` output unchanged) and
`index::tests::query_filtered_unstamped_matches_brute_force_and_keeps_stamps`. The existing
router oracle property (`w15_winv10_route_properties_and_oracle`, which scores every
candidate and validates in score order) now guards the lazy walk.

**Diagnostic timing (non-reference).** [`W2.2/windows-2026-11-23-wb3-perf/`](W2.2/windows-2026-11-23-wb3-perf/):
[`run.sh`](W2.2/windows-2026-11-23-wb3-perf/run.sh) alternates the pre-change binary
(`bc75993`) and the post-change binary, three passes each of the WB3 bench's 100 per-apply
observations; `raw/` holds the CSVs, Criterion lines, run order, binary hashes, load
readings and conditions. Machine: i7-14650HX, Windows 11 Home 10.0.26200, AC power (battery
100%), power scheme `Silent`, CPU-only (resolution, scale and refresh do not apply); CPU
load 0–41% around passes (other sessions' builds; the reading before after-pass 3 came
back empty), so these are not section 2.1 conditions.

About 16.5x faster at p50 on this machine. Phase split of the after build (temporary
instrumentation, each apply on a freshly loaded sheet, about 1.35 ms in all): planner about
0.75 ms (WD4 routing of the 199 rerouted runs about 0.6 ms), normalising the 441 planned
wires about 0.25 ms, inserting them about 0.15 ms, moving the 100 parts about 0.08 ms,
the rest under 0.05 ms each.

**Risk for the Orion re-run.** Orion's 2026-11-23 median p50 (42 ms) was about 2.06x this
machine's pre-change p50. If that ratio held, Orion would read about 2.5 ms p50 and
3.1 ms p99, which still fails WB3's `< 2 ms`. The ratio may differ (the old cost was
dominated by allocation and memory traffic, the new one by routing compute), so only the
re-run decides. If it fails, the remaining cost is spread thinly: routing work per item
inside the candidates' segments, `plan_add_wires`, and wire insertion; a further step would
need a structural change (for example keeping reservations out of the spatial view and
checking them only in rule 2), not more tuning.
