## Timing semantics checked against the pinned source

Read `canvas-plan.md` sections 2/2.1, repository roadmap rules, benchmark `harness.rs`,
and GPUI revision `15d136bf8e72ae43b284183ec46940c009460f5c` before interpreting results.
Relevant upstream files/locations at that revision:

- `crates/gpui/src/profiler.rs`: `FrameTiming::work_start` / `work` (891–908),
  `WindowProfiler::record_present_at` (1482–1559), `FrameTimingCollector` (1616 onward).
  Work starts at the later of signal and dirty time and ends at **present start**.
  Waiting for a platform signal is excluded, however late that signal fires.
  Present intervals use **present end**, only for newly drawn active animation frames.
- `crates/gpui/src/window.rs`: next-frame callbacks execute before drawing (2033 onward);
  `present` (3964) brackets `platform_window.draw` and then records the CPU timestamp.
- `crates/gpui_linux/src/linux/wayland/window.rs`: callback-driven wakeup (1019), mailbox
  preference (588), `draw` (2050) requests the next callback and calls the renderer.
- `crates/gpui_wgpu/src/wgpu_renderer.rs`: `draw` (1087) acquires a surface texture,
  renders, and presents (1165). Acquisition/submission can therefore increase the
  present interval without increasing the reported work span.

These are CPU timestamps, not evidence of compositor scan-out. A delayed Wayland callback,
client descheduling/event dispatch, pre-draw callback work, or platform present call can
produce a large interval with low work. None is proven for PR23's failure.

The benchmark takes its histogram baseline in a next-frame callback between warmup and
the first measured draw. Its cost is excluded from draw/work, but the interval from the
last warmup present to the first measured present is included. This is intentional existing
measurement behavior, not a demonstrated bug. A slow baseline callback remains a testable
hypothesis if a future trace places a miss at measured index 0. No sample is dropped here.

## Instrumentation and bounded experiment

`OMNIA_BENCH_TRACE=1` enables the pinned profiler's frame events for `bench run`. The
report's `diagnostic_trace` holds ordered draw and present events, integer nanoseconds
from a common monotonic anchor, dirty and signal times when available, and the raw
animation interval. Collection/JSON encoding happens during reporting, after measured
histograms and allocation samples have been read. Runtime tracing itself has overhead,
including GPUI task tracing, so enabled reports carry `config.diagnostic_trace=true`.
`bench compare` rejects mixing them with untraced reports (verified exit 2).
The default path does not enable tracing; it adds a null diagnostic field to the report.

No new dependency or GPUI patch. `FrameTimingCollector` is bounded upstream; for these
short runs the analyzer verifies every expected draw is present, all 600 measured frames
have presents, raw intervals agree with histogram buckets/counts, and interval phases sum
exactly. Startup draws may be superseded without a present, so pairing follows GPUI's
pending-frame behavior rather than assuming alternating events from process start.

[diagnostic.sh](T1.6-debug/diagnostic.sh) ran eight serial 600-frame pan runs at 125%:
untraced warmup 60; four traced warmup 60; two traced warmup 600; untraced warmup 60.
Traced runs also used `WAYLAND_DEBUG=client` to preserve callback traffic. Longer warmup
is solely an experimental variable. The campaign ran under
`timeout --signal=TERM --kill-after=15s 300s kde-inhibit --power --screenSaver bash`, with
an EXIT trap restoring the original panel scale. No concurrent benchmark ran.

Hardware: ThinkPad T470, i5-7300U (2 cores / 4 threads), Intel HD Graphics 620 / Mesa ANV
26.2.3-arch1.1, Arch Linux / KDE Wayland, native 1920×1080 at 60.008 Hz. Fullscreen
1536×864 logical at scale 1.25 in every result; no software renderer, no warnings, 600
measured draws, zero ours allocations. All 16 before/after records show AC online,
powersave governors, panel scale 1.25 and DPMS on; power profile interfaces unavailable.
Konsole PID 14873 was present and was left open. Therefore this is diagnostic data outside
the complete section 2.1 gate protocol, additionally limited by tracing overhead and a
single scale/case. No newly opened user app was closed.

The campaign ran approximately 14:33–14:35 EST and exited 0 at 14:35:31.
All eight runs have zero misses. The largest raw traced interval was 22.936100 ms,
measured index 364 with warmup 600: 14.427403 ms from the previous present end to draw
start, 1.836787 ms draw, 0.009951 ms to present start, and 6.661959 ms in the platform
present call. Signal-to-draw was 0.036305 ms. This demonstrates phase separation on a
subthreshold interval; it does not explain the original 49.7746 ms interval.

## Remaining blocker and next evidence

No root cause reproduced; no production rendering/pacing change. Do not retry until green
or reinterpret aggregation. T1.6 needs a causally explained/fixed failure and the complete
unchanged reference protocol, not a passing subset.

The next useful evidence is a **failing** frame trace alongside Wayland callback traffic.
Locate its measured index, signal/dirty times and platform-present span. An index-0 miss
would direct investigation to baseline/warmup transition; a long platform call to surface
acquire/submission; a late signal to callback delivery or client scheduling. Distinguishing
those last two requires a correlated scheduler/compositor trace, not only this CPU timeline.
`perf` was unavailable on Orion and `perf_event_paranoid` was 2; neither was changed.
No compositor or swapchain cause should be claimed without that evidence.
